# Extension Runtime Gateway Model

## 1. Purpose

Phase 8.0 adds one Extension-layer dispatch entrypoint for the execution paths
already present in this repository:

```text
caller
  |
  v
ExtensionRuntimeGateway
  |-- skill.invoke   -> SkillInvoker -> StreamingBridge
  |-- plugin.invoke  -> registered PluginInvocationFacade
  `-- adapter.receive -> registered ExtensionMessageReceiver
          |
          +-> Lifecycle / Health observations
          +-> Metrics
          `-> Event Trace
```

The Gateway coordinates contracts and existing bridges. It is not the
AgentScope/QwenPaw Runtime, does not implement an Agent loop, and does not
discover or start executable code dynamically.

## 2. Runtime boundary

The Extension Runtime Gateway owns:

- explicit operation routing;
- Manifest identity and Extension type checks through `ExtensionRegistry`;
- local lifecycle/health gating;
- creation and validation of `ExtensionRuntimeContext`;
- publishing validated Skill events through the existing Streaming Bridge;
- local metrics and Event Trace observations.

It does not own:

- AgentScope Runtime scheduling, planning, prompts, model calls, or Agent state;
- historical Telegram, WeCom, or WeChat Customer process startup;
- Gateway callback, database, cursor, session, credential, or provider logic;
- Message Model or Streaming protocol definitions;
- PDF Editor algorithms or any other Skill business implementation.

AgentScope integration can later call this Gateway as an Extension host API.
The dependency direction must remain AgentScope Runtime to Extension Gateway,
never Extension Gateway importing or replacing AgentScope Runtime.

## 3. ExtensionRuntimeContext

`core/extensions/runtime/context.py` defines schema
`qwenpaw-extension-runtime-context.v1`:

```text
ExtensionRuntimeContext
  extension_id
  version
  trace_id
  session_id
  artifacts[]
  events[]
```

The context is immutable after construction. Artifact and event identifiers
must be unique. Every attached `StreamEvent` must share the context's
`trace_id` and `session_id`.

For Skill calls, existing request correlation values are retained. Missing
`trace_id` or `session_id` values are generated by the Gateway and inserted
into a new `SkillRequest`; the caller's original request is not mutated. The
completed context contains both input and output artifacts plus the validated
Skill events.

For inbound messages, the context uses the `MessageEvent.trace_id` and
`MessageEvent.session_id`, preserving the Channel Adapter's established
correlation model.

## 4. Dispatch API

`dispatch(operation, extension_id=..., **arguments)` accepts three explicit
operations:

| Operation | Typed method | Extension type | Result |
| --- | --- | --- | --- |
| `skill.invoke` | `invoke_skill()` | Skill | `ExtensionGatewayResult` containing `SkillRuntimeResult` |
| `plugin.invoke` | `invoke_plugin()` | Plugin | `ExtensionGatewayResult` containing facade output |
| `adapter.receive` | `receive_message()` | Adapter or message-bearing Plugin | `ExtensionGatewayResult` containing `MessageEvent`, or `None` |

Explicit operations prevent the Gateway from guessing whether a Plugin should
receive a message, perform an outbound action, or expose only health state.
Wrong Extension types and unknown operations are rejected before business code
is called.

## 5. Skill invocation

The Skill path is:

```text
Registry metadata
  -> Lifecycle/Health check
  -> SkillInvoker.invoke(event_publisher=None)
  -> Context correlation validation
  -> Observability Event Trace
  -> existing StreamingBridge.publish()
  -> ExtensionGatewayResult
```

The Gateway deliberately requests an un-published `SkillRuntimeResult` first.
Only after result/context validation does it publish each `StreamEvent`. This
prevents an event with a mismatched Gateway trace or session from entering the
Streaming Bridge. The returned `published_event_count` reflects the events the
Gateway published.

The SkillInvoker remains the owner of Manifest executor validation and Skill
result rules. The Gateway never imports or copies PDF Editor business logic.

## 6. Plugin invocation

Plugin business calls require an explicitly registered
`PluginInvocationFacade`:

```python
gateway.register_plugin("wecom", facade)
gateway.invoke_plugin(
    "wecom",
    payload={"operation": "send", "text": "..."},
    trace_id="trace-existing",
    session_id="session-existing",
)
```

The facade is injected by the local Extension host. The Gateway does not
resolve a Manifest entrypoint into an import, shell command, Node process, or
network connection. Existing Telegram/WeCom/WeChat Customer bridge wrappers
remain responsible for their provider-specific translation and transport.

If a facade exposes `health_check()`, its existing Plugin Runtime health probe
is used. Otherwise the Gateway uses the local Lifecycle Manager health check.

## 7. Adapter message entry

`register_message_receiver()` accepts an existing object implementing
`receive_message() -> MessageEvent | None`. Adapter manifests and historical
message-bearing Plugins are both supported because WeCom and WeChat Customer
are classified as Plugins while exposing Adapter facades.

Each receive attempt is counted. A successful empty poll returns `None` and is
recorded as `adapter.receive.empty`; it is not a failure. A received message is
recorded as `adapter.message.received` without copying message content into
observability metadata.

## 8. Lifecycle and health integration

Before a business call, the Gateway obtains a `HealthReport`, snapshots it in
`ExtensionHealthStore`, and snapshots the resulting `LifecycleRecord`. An
unhealthy report rejects the call with `ExtensionNotAvailableError` and counts
one failed attempt.

This health gate observes the local simulated lifecycle or an injected
component health probe. It never invokes lifecycle `enable`, `start`, `stop`,
`upgrade`, or `rollback`, and therefore never starts a real historical process.

## 9. Metrics and Trace

Every completed Gateway attempt records exactly one terminal metric outcome:

```text
calls = successes + failures
```

Gateway-level events use the operation context trace:

- `skill.invoke.start`, `skill.invoke.success`, `skill.invoke.failure`;
- `plugin.invoke.start`, `plugin.invoke.success`, `plugin.invoke.failure`;
- `adapter.message.received`, `adapter.receive.empty`,
  `adapter.receive.failure`.

Skill `StreamEvent` records are added to the same Trace before publication.
Trace metadata contains only correlation and safe operation metadata; input
payloads, message text, document content, credentials, and exception messages
are not recorded. Failure traces retain only the exception class name.

## 10. Offline status

Phase 8.0 is a local Extension-host foundation. Tests use fake Skill, Plugin,
Adapter, and Lifecycle components with the real Registry, contract models,
Streaming Bridge, and Observability stores. They do not connect to AgentScope,
provider APIs, historical Gateway processes, databases, cursors, or secrets.

Future production integration must supply supervised Plugin facades and
message receivers explicitly, preserve the current Gateway ownership rules,
and define process-level persistence/export for in-memory observability data.
